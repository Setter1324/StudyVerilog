## 1. 요약

KW STUDY SITE는 **설치 없이 링크로 여는 웹 사이트**로 만들고 GitHub Pages에 올린다. 윈도우 프로그램은 따로 만들지 않는다. 같은 사이트를 브라우저의 "앱으로 설치" 기능으로 창 프로그램처럼 쓸 수 있기 때문이다.

| 항목 | 결정 |
| --- | --- |
| 형태 | 정적 웹 사이트 + 앱 설치(PWA) |
| 실행 엔진 | 브라우저 안에서 도는 Icarus Verilog (WebAssembly). 서버 없음. 0단계에서 검증을 통과했다 |
| 그래픽 | 2D 아이소메트릭. 코드로 그리는 오리지널 블록 스타일 |
| 범위 | 수업 순서대로. 1-2주차 "게이트 마을" 15스테이지가 첫 출시 |
| 배포 | 공개 저장소 `Setter1324/StudyVerilog` → GitHub Pages `https://setter1324.github.io/StudyVerilog/` → COM's 사이트에 링크 |
| 라이선스 | 앱 코드 MIT, 엔진(Icarus Verilog)은 GPL-2.0-or-later 그대로 |
| 구현 | 주찬이 Claude 세션에서 진행한다. 14장의 순서를 따른다 |

이 문서는 11월 16일의 v0.1 설계안을 대체한다. v0.1의 "결정 필요" 3가지는 2장에서 모두 닫았다.

다음 행동은 세 가지다.

1. 주찬: 초안 스테이지 확인, 1-12 회로도 첨부(0.2).
2. 구현 세션: 강의자료로 초안 스테이지 15개를 맞추고, 1-12를 18쪽 회로도로 다시 만든다(14.2의 7번).
3. 구현 세션: 2단계 완료 기준(키보드만으로 15개 통과)을 확인하고 `v0.1.0`을 낸다.

### 2.1 웹으로 가는 이유

- **쓰는 사람:** 링크만 누르면 된다. 맥에서도 되고, 설치 파일 경고를 볼 일이 없다.
- **올리는 사람:** push 하면 GitHub Pages에 자동으로 배포된다. COM's 사이트에는 Apps 목록에 링크만 등록하면 된다. 이미 GitHub Pages에 올린 부원 프로젝트(KW Algorithm Lab)가 Apps에 있다.
- **만드는 쪽:** Claude가 리눅스 환경과 GitHub Actions에서 빌드와 테스트를 끝까지 돌릴 수 있다. 윈도우 설치 파일은 Claude가 직접 실행해 볼 수 없다.
- **프로그램처럼 쓰고 싶을 때:** Chrome과 Edge의 "앱으로 설치"(PWA)로 창과 아이콘이 생긴다. COM's 사이트도 같은 방식을 쓴다.

### 2.2 실행 엔진: 검증을 통과했다

v0.1은 "브라우저에서 바로 쓸 Icarus Verilog 패키지를 확인하지 못했다"는 이유로 PC 로컬 서버에서 시작하려 했다. 다시 조사하니 공개 사례가 여럿 있었다.

| 사례 | 확인한 내용 |
| --- | --- |
| [VeriSim](https://github.com/senolgulgonul/verisim) | Icarus Verilog를 Emscripten으로 WebAssembly로 빌드했다. `ivlpp`, `ivl`, `vvp` 세 단계를 자바스크립트가 차례로 부른다. `$display`·`$monitor` 출력과 VCD 파형이 나온다. GitHub Pages에서 돈다. GPL-2.0 |

| [gogo-fpga/toolchain PR #37](https://github.com/gogo-fpga/toolchain/pull/37) | Icarus Verilog v13.0을 WASI SDK로 빌드하고 CI에서 네이티브 결과와 비교한다. 세 파일 합계 약 2.5 MB(zstd 압축) |

그래서 서버 없이 간다. 게이트 지연(`#3`)까지 수업과 같은 결과가 나오는지는 0단계에서 직접 확인했다(13.1, `engine/README.md`). 6개 모두 로그와 VCD 신호 변화가 같았고, 6번은 같은 시각 안에서 VCD 줄 순서만 달랐다.

검증에 실패했다면 대안은 둘이었다. 이후 엔진 버전을 바꾸다 문제가 생기면 다시 본다.

- **대안 B, 윈도우 프로그램:** Tauri v2의 사이드카 기능으로 네이티브 `iverilog`·`vvp`를 함께 묶는다. 윈도우용 빌드는 [bleyer.org](https://bleyer.org/icarus/)에 있다. 화면 코드는 그대로 쓴다.
- **대안 C, 서버 실행기:** 사용자 코드를 서버에서 돌린다. 격리와 운영 부담이 커서 마지막 선택이다.

### 2.3 그래픽: 그림 파일 대신 코드로 그린다

블록, 건물, 동물을 모두 SVG 다각형 세 면(윗면·왼쪽 면·오른쪽 면)으로 그린다.

- 그림 에셋을 구하거나 그릴 필요가 없다. Claude가 끝까지 만들 수 있는 방식이다.
- 색이 디자인 토큰을 그대로 따른다. 낮과 해 질 녘 팔레트를 바꾸기 쉽다. 구현에서는 면 색을 CSS `color-mix()`로 섞어 토큰 변수를 그대로 쓴다.
- 클릭, 키보드 초점, 자동 테스트가 일반 DOM처럼 된다.
- 첫 화면 시안의 섬이 이 방식으로 그려져 있어 그대로 옮겼다(`src/world/iso.ts`, `island.ts`).

장면이 커져 느려지면 렌더러만 PixiJS로 바꾼다. 그래서 렌더러를 인터페이스 뒤에 둔다(9장). 지금은 장면 계산(`iso.ts`가 만드는 그림 요소 목록)과 그리기(`IsoSvg.tsx`)가 나뉘어 있다.

## 3. 사용자와 UX 원칙

쓰는 사람은 같은 수업을 듣는 학생과 COM's 부원이다. 아래 두 상황을 기준으로 설계한다.

| 상황 | 필요한 것 | 화면이 해 줄 일 |
| --- | --- | --- |
| 수업 직후 10분 복습 | 오늘 배운 개념 하나를 바로 확인 | 첫 화면의 "이어서 하기" 한 번으로 다음 스테이지에 들어간다 |
| 시험 전 범위 복습 | 특정 주차로 바로 이동 | 구역 카드와 스테이지 목록이 주차 이름으로 열려 있고 잠기지 않는다 |

원칙은 여덟 가지다. 화면을 만들다 판단이 갈리면 이 순서로 우선한다.

1. **한 화면에 주 행동 하나.** 첫 화면은 "이어서 하기", 플레이 화면은 "실행"이다.
2. **틀은 조용하게, 월드는 생생하게.** 버튼과 카드는 COM's 사이트의 절제된 스타일을 따른다. 색과 움직임은 월드에 몰아 준다. 바에는 장식을 더하지 않고 월드의 정보(진행, 시간, 결과)를 올린다(6.1).
3. **고치면 바로 보인다.** 실행을 누른 뒤 첫 동물이 움직이기까지 1초 안을 목표로 한다. 더 걸리면 진행 표시를 먼저 띄운다.
4. **틀려도 벌점이 없다.** 오답은 동물이 엉뚱한 곳으로 가는 장면으로 보여 주고, 바로 다시 고칠 수 있다. 목숨, 타이머, 감점은 두지 않는다.
5. **색만으로 말하지 않는다.** 1·0·x·z는 모양과 글자로도 구분된다.
6. **수업 화면과 같은 말을 쓴다.** 파일 이름은 `design.sv`와 `testbench.sv`, 로그는 Icarus Verilog가 내는 그대로 보여 준다.
7. **묻지 않고 시작한다.** 로그인, 설치, 튜토리얼 팝업이 없다. 쓰는 법은 스테이지 1-1 안에서 알려 준다.
8. **키보드만으로 끝까지 간다.** Ctrl+Enter로 실행하고, Tab으로 빈칸과 건물 사이를 옮긴다.

## 4. 화면 구조와 흐름

화면은 네 개(첫 화면, 스테이지 목록, 플레이, 도감)이고 그 위에 뜨는 판이 두 개(결과, 설정)다. 첫 화면에서 한 번 누르면 플레이에 들어가고, 시간 대부분을 거기서 보낸다.

**그림을 글로 옮김 (화면 흐름):** 첫 화면 →(이어서 하기)→ 플레이 →(실행·채점)→ 결과 판 →(다음 스테이지)→ 다시 플레이. 첫 화면 →(구역 카드)→ 스테이지 목록 →(스테이지 열기)→ 플레이. 도감과 설정은 상단 바에서 언제든 연다.

결과 판의 "다음 스테이지"가 플레이로 되돌아가는 고리다. 한 번 들어오면 첫 화면으로 나올 필요가 없다.

| 화면 | 주소 | 담는 것 | 주 행동 | 상태 |
| --- | --- | --- | --- | --- |
| 첫 화면 | `#/` | 이어서 하기, 섬 지도, 값 읽는 법, 구역 카드 | 이어서 하기 | ✅ |
| 스테이지 목록 | `#/stages` | 구역별 스테이지 표. 유형, 완료 표시, 주차 | 스테이지 열기 | ✅ |
| 플레이 | `#/play/v1-04` | 월드, 에디터, 파형, 콘솔 | 실행 | ✅ (본문이 있는 스테이지만. 없으면 "준비 중") |
| 도감 | `#/guide` | 비유 체계와 문법 요약 | 읽기 | 자리표시 |
| 결과 판 | 플레이 위 | 맞음과 틀림, 이유 한 줄, 다음 스테이지 | 다음 스테이지 | ✅ |
| 설정 판 | 상단 바 | 소리, 테마, 진행도 내보내기와 지우기 | 없음 | ⬜ (소리·테마 버튼만 상단 바에 있다) |
| 컴포넌트 보기 | `#/ui` | 7.7절 컴포넌트 13개 | 없음 | ✅ 개발용, 메뉴에 없다 |

주소는 `#` 방식(해시 라우팅)을 쓴다. GitHub Pages와 COM's 하위 경로 어디에 올려도 새로고침이 깨지지 않는다. 파서는 `src/app/route.ts`에 있다.

### 5.5 움직임과 접근성

- 섬 지도의 동물은 길을 따라 한 칸에 0.8초로 걷는다(칸 걷기). 지금 위치 표시는 위아래로 4px 떠 있다. (✅ PR #11. 플레이 장면은 한 박자 걷기, 7.9)
- 구역에 마우스를 올리면 그 구역이 4px 떠오르고 이름표가 뜬다. (지금은 핀 위에 이름표가 뜨고 구역 카드가 4px 떠오른다)
- `prefers-reduced-motion`이면 모든 움직임을 멈춘다.
- 섬 지도는 그림으로 다루고 설명글을 단다. 같은 이동은 구역 카드가 제공한다.
- 버튼과 링크는 실제 `<button>`과 `<a>`로 만든다. 글자 대비는 4.5:1 이상이다.

## 6. 플레이 화면 사양

플레이 화면은 수업에서 쓰는 EDA Playground의 구성(`design.sv`, `testbench.sv`, 로그, 파형)에 월드를 붙인 것이다. 구현은 `src/app/play/`다.

### 6.1 배치 (폭 1100px 이상)

| 영역 | 위치 | 내용 |
| --- | --- | --- |
| 상단 바 | 위, 56px | 뒤로, 구역 핀, 윗줄(`게이트 마을 · 1-4`와 유형 꼬리표), 제목, 가운데 **징검다리**, 소리, 힌트, **실행** 버튼. 아래 선 자리에 **해의 길** |
| 월드 | 왼쪽 위, 폭 55% | 스테이지 장면. 재생 중에만 알파카가 걷는다(7.9). 아래에 시간 슬라이더, 재생·정지, 속도(0.5× · 1× · 2×), "끝으로" |
| 에디터 | 오른쪽 위, 폭 45% | 문제 설명(접을 수 있음), 힌트, 탭 `design.sv` / `testbench.sv`, 빈칸과 잠금 줄, 문제 칸(예측·타이밍) |
| 파형 | 왼쪽 아래 | 신호별 파형. 시간 슬라이더와 같은 시각선. 누르면 그 시각으로 간다 |
| 콘솔 | 오른쪽 아래 | `$monitor`·`$display` 출력과 컴파일 오류. 지금 시각의 줄을 강조한다 |

상단 바는 장식을 더하지 않고 월드의 정보를 올린다: 어디까지 왔나(징검다리), 지금 몇 시인가(해의 길), 어떻게 됐나(통과·실패). 구현은 `src/ui/StageStones.tsx`, `src/ui/SunTrack.tsx`다(PR #15).

- **징검다리:** 구역의 스테이지 수만큼 작은 블록. 통과한 칸은 구역 색으로 채우고, 지금 칸은 크게 그리고 위에 ▼(섬 지도의 "지금 위치"와 같은 모양)를 단다. 누르면 그 스테이지로 간다. `<nav aria-label="이 구역의 스테이지">` 안의 링크이고 지금 칸은 `aria-current="step"`이다. 누르는 영역은 28×44px. Tab 한 번에 묶음에 닿고(지금 칸만 Tab 순서에 있다) ←→·Home·End로 칸을 옮긴다.
- **해의 길:** 바 아래의 3px 트랙. 왼쪽 끝이 t=0, 오른쪽 끝이 `$finish`. 해(지름 10px, 상자색)가 재생 시각을 따라 가고 지나온 만큼 칠한다. 장식으로 다룬다(`aria-hidden`).
- 폭 1100px 미만에서는 징검다리를 숨기고 윗줄에 `4 / 15`를 되돌린다. 해의 길은 남긴다.
- 사이트 상단 바(`TopBar.tsx`)는 홈이 아닌 화면에서 도구 앞에 `1-4 이어서` 알약을 둔다.

| 상태 | 해의 길 | 징검다리 |
| --- | --- | --- |
| 실행 전 | 빈 트랙 | 지금 칸 강조 |
| 엔진 받기, 컴파일 | 좌우로 흐른다(받은 비율을 알게 되면 왼쪽에서 찬다) | 그대로 |
| 재생 중 | 해가 시각을 따라 간다 | 그대로 |
| 해가 짐(`$finish`) | 해가 오른쪽 끝에서 지고, 바 바탕이 월드와 같은 노을빛 | 그대로 |
| 통과 | 트랙이 `--success`로 한 번 찬다 | 지금 칸이 채워지고 ▼가 다음 칸으로 뛴다. 처음 통과한 칸은 해가 진 뒤에 채운다 |
| 실패 | 그대로 | 지금 칸이 좌우로 두 번 흔들린다 |

움직임 줄이기에서는 뜀·흔들림·흐름이 없고 해는 자리만 옮긴다. 상단 바의 다른 안(가볍게: 유형 칩과 진행 막대만, 과감하게: 바 전체를 하늘로)은 시간과 결과가 보이지 않거나 코드를 읽는 데 방해가 되어 고르지 않았다.

폭 1100px 미만에서는 월드, 에디터, 콘솔, 파형 순서로 세로로 쌓는다. 폰에서는 예측형과 숫자 답 스테이지가 편하고, 코드를 고치는 스테이지에는 "PC가 편해요"라고 알려 준다(남은 일).

강의 흐름도 그대로 따른다. 1-2주차 앞부분은 한 모듈에 설계와 테스트벤치를 같이 쓰므로 탭이 하나다. "design/testbench 분리"(스테이지 1-13)부터 탭이 둘이다.

### 6.2 실행 한 번의 흐름

1. 실행을 누른다(Ctrl+Enter). 버튼이 "실행 중"으로 바뀐다. 예측·타이밍형은 답을 먼저 골라야 한다. 보스처럼 `afterRun`인 문제는 실행해서 파형을 본 뒤에 고르고 다시 실행한다.
2. 엔진이 컴파일한다(해의 길이 좌우로 흐른다). 오류면 콘솔에 줄 번호와 함께 띄우고, 에디터의 그 줄에 표시하고 멈춘다.
3. 성공이면 콘솔에 로그가 찍히고 타임라인이 만들어진다.
4. 해가 뜨고(t=0) 월드가 재생된다. 1틱은 240ms로 언제나 같다. 알파카가 값을 싣고 한 박자에 걷고, 건물은 지연 칸을 채우고, 파형의 시각선과 해의 길이 함께 움직인다(7.9).
5. `$finish` 시각에 해가 지고(월드 하늘색과 바 바탕이 노을빛이 된다) 알파카가 길 가운데에 서고 결과 판이 뜬다.
6. 맞으면 "다음 스테이지"를 보여 준다. 틀리면 어디서 달라졌는지 한 줄로 말하고("t=15에서 E가 1이어야 하는데 0이에요") "그 시각으로 가기"를 준다.

### 7.8 움직임과 소리

- 화면 전환과 버튼은 180ms ease-out이다.
- 월드는 시뮬레이션 1틱을 240ms로 재생한다. 변화가 없는 틱도 같은 길이다. 속도는 0.5×, 1×, 2×다(7.9).
- 정답이면 건물이 한 번 튀고(120ms), 오답이면 동물이 제자리에서 고개를 젓는다. (남은 일)
- `prefers-reduced-motion`이면 알파카는 길 가운데에 서 있고, 바의 뜀·흔들림·흐름도 없다.
- 소리는 기본이 꺼짐이다. 켜면 발소리, 건물 통과음, 정답 종, 오답, x 안개, 해 지는 소리 여섯 가지가 난다. 음원 파일 없이 코드에서 만든다. (✅ PR #11: Web Audio로 실행, 값 변화 1/0, 안개, 정답 종, 오답, 컴파일 오류. ZzFX 대신 직접 만들었다. 배경음은 `content/audio.json`)

### 7.9 움직임 규칙: 박자 시계

한 줄 원칙: **거리는 속도가 흡수하고, 시간은 코드만 정한다.** 구현은 `src/world/beat.ts`(값과 시계 함수), `walkers.ts`(`tripPose`), `Walkers.tsx`, `src/sim/delays.ts`다(PR #13, #14).

1. **한 박자 규칙.** 플레이 장면의 모든 길은 길이와 상관없이 출발에서 도착까지 한 박자다. 긴 길의 알파카는 빨리, 짧은 길의 알파카는 천천히 걷는다. 그래서 길마다 같은 순간에 건물에 도착하고, 어긋남이 생기지 않는다. 섬 지도는 예외로 한 칸에 0.8초(칸 걷기)로 늘 걷는다.
2. **시계는 하나, 쌓지 않는다.** 재생 시계는 재생을 시작한(속도를 바꾼) 순간의 틱과 시각을 기준점으로 잡고, `requestAnimationFrame`에서 `지금 틱 = 기준 틱 + 경과 × 속도 ÷ 240ms`로 계산한다. 정수 틱이 바뀔 때만 화면 상태를 바꾼다. 걷기도 같은 기준점에서 박자 위치(`틱 ÷ 10 + 0.5`)를 얻는다. 컴포넌트마다 타이머를 두지 않는다.
3. **시간은 코드만 정한다.** 화면에서 시간 차이가 나는 곳은 코드에 `#N`을 쓴 곳뿐이다. 길(wire)에는 지연이 없으니 걷는 시간은 건드리지 않고, 지연은 건물에서 N틱으로 센다.
4. **틱은 언제나 같은 길이다.** `#3`은 `#2`의 1.5배로 보인다(1-4의 t=10→13은 0.72초, t=13→15는 0.48초).
5. **재생 중에만 걷는다.** 실행 전, 멈춤, 해가 진 뒤에는 길 가운데에 선다. 서기와 걷기 사이는 180ms로 잇는다. 값이 바뀌는 틱(10의 배수)에 알파카가 길 가운데에 있어서 값이 바뀌는 순간이 가장 잘 보인다.

| 이름 | 값 | 이유 |
| --- | --- | --- |
| 한 박자 `BEAT_TICKS` | 10틱 | 수업 테스트벤치가 `#10`마다 값을 바꾼다. 다른 간격이면 장면의 `beatTicks`(1-10은 5) |
| 1틱 `TICK_MS` | 240ms | 한 박자가 2.4초. 실제 화면을 보고 바꾸는 값은 이것 하나다 |
| 길마다 알파카 | 1마리 | 모든 길이 같은 수여야 같이 도착한다 |
| 한 박자 걸음 수 | 6걸음 | 모든 알파카가 발을 맞춘다 |
| 나타나고 사라지는 시간 | 박자의 앞뒤 8% | 거리 기준이면 빠른 알파카가 늦게 사라진다 |
| 한 장면의 길 길이 | 2~6칸, 가장 긴 길이 가장 짧은 길의 2.5배 이하 | 속도 차이가 너무 커지지 않게. 테스트가 경고로 알린다 |

**지연 칸.** `delaysBySignal`이 실행한 코드(주석 제외)에서 `or #3 (w1, A, B);`, `assign #3 w1 = ...;` 꼴을 찾아 출력 신호별 지연을 읽는다(프리미티브는 첫 포트가 출력, 정수 하나짜리만). 건물의 출력 신호가 시각 c에 바뀌면 그 건물은 c − N부터 c 직전까지 "지나는 중"이다(`passingAt`). 건물 이름표 아래에 칸 N개를 그리고 한 틱에 하나씩 채운다. N이 6을 넘으면 남은 틱 수를 적는다. 월드 설명글에도 `OR #3, 3틱 중 2틱째`라고 단다. 표시용이고 채점은 결과로만 한다. 빈칸에 `#5`를 쓰면 칸도 5개, 실제 변화도 5틱 뒤라 화면과 결과가 늘 맞는다.

**이름표 층.** 길 이름표, 건물 이름표, 지연 칸은 걷는 알파카 위 층에 그린다(`IsoSvg`의 `top`).

고르지 않은 안: 길 길이를 전부 같게(장면을 그리기 어렵다), 짧은 길의 알파카를 기다리게(서 있는 시간이 길마다 달라 어수선하다), 값이 바뀔 때만 걷기(걷는 동안 값이 파형의 시각과 어긋난다), 지연을 걷는 시간이나 출발 시각 차이로 보여 주기(걷기는 되풀이되어 박자의 배수인 지연이 보이지 않는다).

### 8.2 무엇을 비우는가

1. 한 스테이지는 개념 하나다. 그 슬라이드가 가르치는 한 가지만 비운다.
2. 강의자료에서 강조한 줄이 빈칸 후보다. 예: `or #3(w1,A,B);`, `test ins_name(H,A,B,C);`, `$dumpvars(1);`, `output reg [1:0]Y;`, `casez(D)`.
3. 교수님이 비워 둔 칸은 그대로 스테이지로 삼는다. 1-2주차 18쪽(회로도를 보고 게이트 작성), 6-7주차 5쪽(prefix tree의 `G_ij` 연결).
4. 점점 넓힌다. 토큰 하나, 한 줄, 블록, 파일 전체 순서다.
5. 빈칸이 아닌 줄은 초반에 잠그고, 설계형에서 푼다.

## 9. 기술 설계

서버는 없다. 사용자의 코드는 브라우저 안의 Icarus Verilog가 돌리고, 결과를 "타임라인"이라는 한 형식으로 바꿔 월드·파형·채점기가 함께 쓴다.

**그림을 글로 옮김 (구조):** 스테이지 데이터(JSON: 시작 코드, 장면, 채점 규칙) →(시작 코드)→ 에디터(design.sv, testbench.sv) →(실행)→ Runner(Web Worker 안에서 ivlpp → ivl → vvp) →(로그, VCD)→ 타임라인(시각마다 신호 값) → 월드, 파형, 채점기. Runner는 갈아 끼울 수 있다(네이티브, 미리 계산한 결과).

장면과 채점 규칙도 스테이지 데이터에서 온다. 화면 코드는 `Runner`와 `Timeline` 두 형식만 알고, 엔진이 무엇인지는 모른다.

### 9.2 Runner: 엔진을 갈아 끼우는 경계

`src/runner/types.ts`에 있다.

```ts
export interface RunRequest {
  files: { name: string; text: string }[]; // design.sv, testbench.sv
  top: string;                             // 최상위 모듈 이름
  limits?: { simTime?: number; logLines?: number; wallMs?: number };
}
export interface RunResult {
  ok: boolean;                 // 컴파일 성공 여부
  stage: 'compile' | 'run';
  log: string;                 // $monitor, $display 출력
  diagnostics: { file: string; line: number; message: string }[];
  vcd?: string;                // dump.vcd 원문
  timedOut: boolean;
}
export interface Runner { run(req: RunRequest): Promise<RunResult>; }
```

구현은 셋이다. `WasmRunner`(`wasmRunner.ts` + `worker.ts`)가 기본이고, `FixtureRunner`는 미리 계산한 결과를 돌려주는 테스트용이며(⬜, `engine/golden/*/native/`가 그 데이터다), `NativeRunner`는 대안 B를 쓸 때만 만든다.

세 단계 호출은 `src/runner/iverilog.ts`의 `runIverilog()`에 있고, 브라우저 워커와 Node 골든 테스트가 같은 코드를 쓴다. ivl 설정 파일은 iverilog 드라이버를 흉내 내고 `-g2012`(SystemVerilog-2012)로 컴파일한다.

스테이지 1-14에서 `$dumpvars`를 배우기 전에는 코드에 파형 덤프 줄이 없다. 그동안은 Runner가 덤프용 모듈(`__kwss_dump`)을 함께 컴파일해서 VCD를 얻는다. Icarus Verilog는 인스턴스가 없는 모듈을 최상위로 다루므로 따로 연결할 필요가 없다.

### 9.3 타임라인: 화면이 쓰는 공통 형식

### 9.5 제한값과 엔진 파일

- 시뮬레이션 시간 10,000틱, 로그 2,000줄, 실행 5초가 시작값이다(`DEFAULT_LIMITS`). 시간 상한은 감시 모듈(`__kwss_guard`: `initial #10000 $finish;`)을 함께 컴파일해서 건다. 그래도 워커가 답하지 않으면 워커를 끝내고 새로 만든다.
- 엔진 파일(js·wasm 세 쌍)은 사이트의 `engine/` 폴더에 있고, 첫 실행 때 받아 브라우저 캐시에 둔다. 플레이 화면에 들어오면 미리 받기 시작한다(`warmUp`). 진행 표시는 상단 바의 해의 길이 맡는다(실행 중에 좌우로 흐른다. 받은 비율을 Runner가 알려 주면 왼쪽에서 차게 바꾼다).
- 엔진 파일은 저장소에 넣지 않는다. 빌드 때 `node engine/fetch-engine.mjs public/engine`이 이 저장소의 `engine-v0.1.0` Release에서 받아 sha256을 확인한다(`engine/engine.lock.json`). 새 엔진은 `engine.yml`을 `release_tag`와 함께 수동 실행해 내고 lock 파일을 바꾼다.
- 워커는 스레드와 `SharedArrayBuffer` 없이 돈다. GitHub Pages에서는 그에 필요한 응답 헤더를 설정할 수 없다.
- 사용자에게 보이는 로그와 오류에서는 감시·덤프 모듈의 흔적을 지우고, 파일 경로를 이름만 남긴다(`testbench.sv:14:`).

### 9.6 C/C++로 넓힐 때

타임라인의 "시각"을 "실행한 줄의 순서"로, "신호"를 "변수와 메모리"로 바꾸면 같은 화면을 쓸 수 있다. 집은 메모리 칸, 표지판은 포인터, 연립주택은 배열이 된다.

실행 방법은 그때 정한다. COM's 사이트에는 회원용 C·Java·Python 실행기가 이미 있어서, 이 사이트를 COM's 하위 경로로 옮기면 그것을 쓰는 길도 열린다.

## 13. 로드맵과 완료 기준

첫 출시는 2단계가 끝나는 때다. 날짜는 정하지 않았고, 각 단계는 완료 기준을 통과해야 다음으로 넘어간다.

**그림을 글로 옮김 (로드맵):** 0 엔진 검증 →[관문: 골든 테스트 6개 일치]→ 1 세로 한 줄 →[관문: Pages에서 1-1 통과]→ 2 구역 1 완성 →[관문: v0.1.0 출시, COM's Apps 등록]→ 3 깊이 더하기 → 4 구역 2~6. 이후 선택: 5 앱 설치와 자유 모드, 6 C/C++ 팩.

여기의 "단계"(0~6)는 제품 로드맵이고, 14.2절의 "번호"(1~7)는 작업 순서다. 지금은 작업 순서 1~6번이 끝났고 7번(스테이지 채우기)은 15개 초안까지 했다. 로드맵으로는 1단계까지 끝났고 2단계 중이다.

| 단계 | 내용 | 완료 기준 | 상태 |
| --- | --- | --- | --- |
| 0 엔진 검증 | 골든 프로그램 6개를 브라우저 엔진과 네이티브 Icarus Verilog로 돌려 비교 | 로그와 VCD가 같다. CI에서 자동으로 확인된다 | ✅ PR #2, #3 |

## 15. 위험과 대응, 저작권과 라이선스

가장 큰 위험이던 "브라우저 엔진의 결과가 수업과 다른 경우"는 0단계에서 골든 6개로 확인했다. 구역마다 새 문법의 골든을 더해 계속 확인한다.

| 위험 | 대응 |
| --- | --- |
| 브라우저 엔진의 결과가 수업(EDA Playground)과 다르다 | 골든 테스트로 확인한다. 버전 차이로 생기는 차이는 도감에 적는다. 풀리지 않으면 대안 B로 간다 |
| 수업에서 쓴 문법 중 엔진이 지원하지 않는 것이 있다 | 구역을 만들기 전에 그 문법의 골든 프로그램부터 돌린다 |
| 엔진 파일을 받느라 첫 실행이 느리다 | 첫 실행 때만 받고 캐시한다. 플레이 화면에 들어오면 미리 받는다. 예측형 스테이지는 미리 계산한 결과로 엔진 없이 여는 방법도 있다 |
| 스테이지마다 장면을 손으로 만드는 부담 | 장면은 작업장·길·집 배치(JSON)로 쓴다(`SceneSpec`) |
| 범위가 크다(여섯 구역) | 구역 1만으로 출시한다. 그 뒤는 데이터를 더하는 일이다 |
| 폰에서 코드 편집이 불편하다 | 폰에서는 예측형과 숫자 답을 권하고 나머지는 PC를 안내한다 |
| 브라우저 저장이 지워져 진행도를 잃는다 | 설정 판에 진행도 내보내기와 가져오기를 둔다 |
| 끝나지 않는 코드 | 감시 모듈로 시간 상한을 걸고, 그래도 안 끝나면 워커를 끝낸다(9.5) |
| 세션 환경에서 npm·일부 GitHub API가 막힌다 | CI에 맡기고, GitHub 웹 설정은 주찬이 한다(0.3) |
| 초안 스테이지의 문구·정답이 수업과 다르다 | `draft` 표시를 두고 주찬이 강의자료로 확인한 뒤 지운다 |

### 15.1 저작권과 라이선스

법률 자문이 아니라 오픈소스에서 흔히 따르는 방식을 정리한 것이다.

- **앱 코드: MIT로 확정**(2026-11-16, 주찬). 저작권 표시는 `Copyright (c) 2026 김주찬`.
- **엔진:** Icarus Verilog는 GPL-2.0-or-later다. wasm을 사이트로 배포하면 그 소스도 제공해야 한다. 고정한 커밋·패치·빌드 스크립트를 `engine/`에 두고, `engine/` 안에 GPL 전문(`engine/COPYING`)을 둔다. 엔진은 워커에서 별도 프로그램으로 돌고 화면 코드는 그것을 불러 쓰기만 하므로, 화면 코드는 MIT로 둔다. 엔진에 넣는 패치는 GPL을 따른다.
- **강의자료:** PDF와 캡처는 사이트와 저장소에 싣지 않는다. 문제는 같은 개념을 새 코드로 다시 쓴다. 강의 코드를 거의 그대로 써야 하는 스테이지는 교수님께 먼저 여쭤본다.
- **그림과 소리:** 마인크래프트의 텍스처·캐릭터·효과음은 Mojang 소유라 쓰지 않는다. 그림은 직접 그리고, 밖에서 가져오는 에셋은 CC0만 쓴다.
- **글꼴:** Pretendard, JetBrains Mono, D2Coding은 OFL이다. 라이선스 파일을 글꼴과 함께 둔다. 예약 글꼴 이름 조항 때문에 직접 서브셋하지 않는다(7.5).
- **이름과 색:** COM's의 색을 쓰지만 학교나 동아리의 공식 사이트로 보이지 않게 한다. 바닥글에 "COM's 부원 프로젝트"라고 적는다.
