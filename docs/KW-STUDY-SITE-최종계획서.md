## 1. 요약

KW STUDY SITE는 **설치 없이 링크로 여는 웹 사이트**로 만들고 GitHub Pages에 올린다. 윈도우 프로그램은 따로 만들지 않는다. 같은 사이트를 브라우저의 "앱으로 설치" 기능으로 창 프로그램처럼 쓸 수 있기 때문이다.

| 항목 | 결정 |
| --- | --- |
| 형태 | 정적 웹 사이트 + 앱 설치(PWA) |
| 실행 엔진 | 브라우저 안에서 도는 Icarus Verilog (WebAssembly). 서버 없음. 0단계에서 검증을 통과했다 |
| 그래픽 | 2D 아이소메트릭. 코드로 그리는 오리지널 블록 스타일 |
| 범위 | 수업 순서대로. 1-2주차 "게이트 마을" 15스테이지가 첫 출시 |
| 배포 | 공개 저장소 `Setter1324/StudyVerilog` → GitHub Pages `https://setter1324.github.io/StudyVerilog/` → COM's 사이트에 링크 |
| 라이선스 | 앱 코드 MIT, 엔진(Icarus Verilog)은 GPL-2.0-or-later 그대로 |
| 구현 | 주찬이 Claude 세션에서 진행한다. 14장의 순서를 따른다 |

이 문서는 11월 16일의 v0.1 설계안을 대체한다. v0.1의 "결정 필요" 3가지는 2장에서 모두 닫았다.

다음 행동은 세 가지다.

1. 주찬: 초안 스테이지 확인, 1-12 회로도 첨부(0.2).
2. 구현 세션: 강의자료로 초안 스테이지 15개를 맞추고, 1-12를 18쪽 회로도로 다시 만든다(14.2의 7번).
3. 구현 세션: 2단계 완료 기준(키보드만으로 15개 통과)을 확인하고 `v0.1.0`을 낸다.

### 2.1 웹으로 가는 이유

- **쓰는 사람:** 링크만 누르면 된다. 맥에서도 되고, 설치 파일 경고를 볼 일이 없다.
- **올리는 사람:** push 하면 GitHub Pages에 자동으로 배포된다. COM's 사이트에는 Apps 목록에 링크만 등록하면 된다. 이미 GitHub Pages에 올린 부원 프로젝트(KW Algorithm Lab)가 Apps에 있다.
- **만드는 쪽:** Claude가 리눅스 환경과 GitHub Actions에서 빌드와 테스트를 끝까지 돌릴 수 있다. 윈도우 설치 파일은 Claude가 직접 실행해 볼 수 없다.
- **프로그램처럼 쓰고 싶을 때:** Chrome과 Edge의 "앱으로 설치"(PWA)로 창과 아이콘이 생긴다. COM's 사이트도 같은 방식을 쓴다.

### 2.2 실행 엔진: 검증을 통과했다

v0.1은 "브라우저에서 바로 쓸 Icarus Verilog 패키지를 확인하지 못했다"는 이유로 PC 로컬 서버에서 시작하려 했다. 다시 조사하니 공개 사례가 여럿 있었다.

| 사례 | 확인한 내용 |
| --- | --- |
| [VeriSim](https://github.com/senolgulgonul/verisim) | Icarus Verilog를 Emscripten으로 WebAssembly로 빌드했다. `ivlpp`, `ivl`, `vvp` 세 단계를 자바스크립트가 차례로 부른다. `$display`·`$monitor` 출력과 VCD 파형이 나온다. GitHub Pages에서 돈다. GPL-2.0 |
| [SynthWave](https://github.com/puru2k/synthwave) | 같은 엔진을 Web Worker에서 돌린다. React + TypeScript + Vite. main에 push 하면 GitHub Pages로 배포된다 |
| [gogo-fpga/toolchain PR #37](https://github.com/gogo-fpga/toolchain/pull/37) | Icarus Verilog v13.0을 WASI SDK로 빌드하고 CI에서 네이티브 결과와 비교한다. 세 파일 합계 약 2.5 MB(zstd 압축) |

그래서 서버 없이 간다. 게이트 지연(`#3`)까지 수업과 같은 결과가 나오는지는 0단계에서 직접 확인했다(13.1, `engine/README.md`). 6개 모두 로그와 VCD 신호 변화가 같았고, 6번은 같은 시각 안에서 VCD 줄 순서만 달랐다.

검증에 실패했다면 대안은 둘이었다. 이후 엔진 버전을 바꾸다 문제가 생기면 다시 본다.

- **대안 B, 윈도우 프로그램:** Tauri v2의 사이드카 기능으로 네이티브 `iverilog`·`vvp`를 함께 묶는다. 윈도우용 빌드는 [bleyer.org](https://bleyer.org/icarus/)에 있다. 화면 코드는 그대로 쓴다.
- **대안 C, 서버 실행기:** 사용자 코드를 서버에서 돌린다. 격리와 운영 부담이 커서 마지막 선택이다.

### 2.3 그래픽: 그림 파일 대신 코드로 그린다

블록, 건물, 동물을 모두 SVG 다각형 세 면(윗면·왼쪽 면·오른쪽 면)으로 그린다.

- 그림 에셋을 구하거나 그릴 필요가 없다. Claude가 끝까지 만들 수 있는 방식이다.
- 색이 디자인 토큰을 그대로 따른다. 낮과 해 질 녘 팔레트를 바꾸기 쉽다. 구현에서는 면 색을 CSS `color-mix()`로 섞어 토큰 변수를 그대로 쓴다.
- 클릭, 키보드 초점, 자동 테스트가 일반 DOM처럼 된다.
- 첫 화면 시안의 섬이 이 방식으로 그려져 있어 그대로 옮겼다(`src/world/iso.ts`, `island.ts`).

장면이 커져 느려지면 렌더러만 PixiJS로 바꾼다. 그래서 렌더러를 인터페이스 뒤에 둔다(9장). 지금은 장면 계산(`iso.ts`가 만드는 그림 요소 목록)과 그리기(`IsoSvg.tsx`)가 나뉘어 있다.

## 3. 사용자와 UX 원칙

쓰는 사람은 같은 수업을 듣는 학생과 COM's 부원이다. 아래 두 상황을 기준으로 설계한다.

| 상황 | 필요한 것 | 화면이 해 줄 일 |
| --- | --- | --- |
| 수업 직후 10분 복습 | 오늘 배운 개념 하나를 바로 확인 | 첫 화면의 "이어서 하기" 한 번으로 다음 스테이지에 들어간다 |
| 시험 전 범위 복습 | 특정 주차로 바로 이동 | 구역 카드와 스테이지 목록이 주차 이름으로 열려 있고 잠기지 않는다 |

원칙은 여덟 가지다. 화면을 만들다 판단이 갈리면 이 순서로 우선한다.

1. **한 화면에 주 행동 하나.** 첫 화면은 "이어서 하기", 플레이 화면은 "실행"이다.
2. **틀은 조용하게, 월드는 생생하게.** 버튼과 카드는 COM's 사이트의 절제된 스타일을 따른다. 색과 움직임은 월드에 몰아 준다. 바에는 장식을 더하지 않고 월드의 정보(진행, 시간, 결과)를 올린다(6.1).
3. **고치면 바로 보인다.** 실행을 누른 뒤 첫 동물이 움직이기까지 1초 안을 목표로 한다. 더 걸리면 진행 표시를 먼저 띄운다.
4. **틀려도 벌점이 없다.** 오답은 동물이 엉뚱한 곳으로 가는 장면으로 보여 주고, 바로 다시 고칠 수 있다. 목숨, 타이머, 감점은 두지 않는다.
5. **색만으로 말하지 않는다.** 1·0·x·z는 모양과 글자로도 구분된다.
6. **수업 화면과 같은 말을 쓴다.** 파일 이름은 `design.sv`와 `testbench.sv`, 로그는 Icarus Verilog가 내는 그대로 보여 준다.
7. **묻지 않고 시작한다.** 로그인, 설치, 튜토리얼 팝업이 없다. 쓰는 법은 스테이지 1-1 안에서 알려 준다.
8. **키보드만으로 끝까지 간다.** Ctrl+Enter로 실행하고, Tab으로 빈칸과 건물 사이를 옮긴다.

## 4. 화면 구조와 흐름

화면은 다섯 개(첫 화면, 스테이지 목록, 플레이, 자유 Verilog, 도감)이고 그 위에 뜨는 판이 두 개(결과, 설정)다. 첫 화면에서 한 번 누르면 플레이에 들어가고, 시간 대부분을 거기서 보낸다.

**그림을 글로 옮김 (화면 흐름):** 첫 화면 →(이어서 하기)→ 플레이 →(실행·채점)→ 결과 판 →(다음 스테이지)→ 다시 플레이. 첫 화면 →(구역 카드)→ 스테이지 목록 →(스테이지 열기)→ 플레이. 자유 Verilog, 도감, 설정은 상단 바에서 언제든 연다.

결과 판의 "다음 스테이지"가 플레이로 되돌아가는 고리다. 한 번 들어오면 첫 화면으로 나올 필요가 없다.

| 화면 | 주소 | 담는 것 | 주 행동 | 상태 |
| --- | --- | --- | --- | --- |
| 첫 화면 | `#/` | 이어서 하기, 섬 지도, 값 읽는 법, 구역 카드 | 이어서 하기 | ✅ |
| 스테이지 목록 | `#/stages` | 구역별 스테이지 표. 유형, 완료 표시, 주차 | 스테이지 열기 | ✅ |
| 플레이 | `#/play/v1-04` | 월드, 에디터, 파형, 콘솔 | 실행 | ✅ (본문이 있는 스테이지만. 없으면 "준비 중") |
| 자유 Verilog | `#/free` | 에디터 두 탭, 파형, 콘솔. 채점과 힌트가 없는 연습장(6.4) | 실행 | ✅ PR #20 (1차) |
| 도감 | `#/guide` | 비유 체계와 문법 요약 | 읽기 | 자리표시 |
| 결과 판 | 플레이 위 | 맞음과 틀림, 이유 한 줄, 다음 스테이지 | 다음 스테이지 | ✅ |
| 설정 판 | 상단 바 | 소리, 테마, 진행도 내보내기와 지우기 | 없음 | ⬜ (소리·테마 버튼만 상단 바에 있다) |
| 컴포넌트 보기 | `#/ui` | 7.7절 컴포넌트 13개, 넓은 건물 견본 3개(9.4) | 없음 | ✅ 개발용, 메뉴에 없다 |

주소는 `#` 방식(해시 라우팅)을 쓴다. GitHub Pages와 COM's 하위 경로 어디에 올려도 새로고침이 깨지지 않는다. 파서는 `src/app/route.ts`에 있다. `?` 뒤는 따로 읽는다. 개발용으로 `#/play/v1-04?ms=5400`은 실행한 뒤 대본의 그 위치(ms)를 그리고 멈춘다(7.9).

### 5.5 움직임과 접근성

- 섬 지도의 동물은 길을 따라 한 칸에 0.8초로 걷는다(칸 걷기). 지금 위치 표시는 위아래로 4px 떠 있다. (✅ PR #11. 플레이 장면은 순차 재생, 7.9)
- 구역에 마우스를 올리면 그 구역이 4px 떠오르고 이름표가 뜬다. (지금은 핀 위에 이름표가 뜨고 구역 카드가 4px 떠오른다)
- `prefers-reduced-motion`이면 모든 움직임을 멈춘다.
- 섬 지도는 그림으로 다루고 설명글을 단다. 같은 이동은 구역 카드가 제공한다.
- 버튼과 링크는 실제 `<button>`과 `<a>`로 만든다. 글자 대비는 4.5:1 이상이다.

### 6.1 배치 (폭 1100px 이상)

상단 바는 장식을 더하지 않고 월드의 정보를 올린다: 어디까지 왔나(징검다리), 지금 몇 시인가(해의 길), 어떻게 됐나(통과·실패). 구현은 `src/ui/StageStones.tsx`, `src/ui/SunTrack.tsx`다(PR #15).

- **징검다리:** 구역의 스테이지 수만큼 작은 블록. 통과한 칸은 구역 색으로 채우고, 지금 칸은 크게 그리고 위에 ▼(섬 지도의 "지금 위치"와 같은 모양)를 단다. 누르면 그 스테이지로 간다. `<nav aria-label="이 구역의 스테이지">` 안의 링크이고 지금 칸은 `aria-current="step"`이다. 누르는 영역은 28×44px. Tab 한 번에 묶음에 닿고(지금 칸만 Tab 순서에 있다) ←→·Home·End로 칸을 옮긴다.
- **해의 길:** 바 아래의 3px 트랙. 왼쪽 끝이 t=0, 오른쪽 끝이 `$finish`. 해(지름 10px, 상자색)가 재생 시각을 따라 가고 지나온 만큼 칠한다. 장식으로 다룬다(`aria-hidden`).
- 폭 1100px 미만에서는 징검다리를 숨기고 윗줄에 `4 / 15`를 되돌린다. 해의 길은 남긴다.
- 사이트 상단 바(`TopBar.tsx`)는 홈이 아닌 화면에서 도구 앞에 `1-4 이어서` 알약을 둔다.
- 징검다리의 칸 가운데 점은 정답을 보고 통과한 스테이지다(6.3). 감점이 아니라 표시다.
- 상단 바의 전구(힌트)는 도움 칸으로 가서 다음 힌트를 연다. 좁은 화면에서는 에디터가 월드 아래에 있어서 남겼다.

| 상태 | 해의 길 | 징검다리 |
| --- | --- | --- |
| 실행 전 | 빈 트랙 | 지금 칸 강조 |
| 엔진 받기, 컴파일 | 좌우로 흐른다(받은 비율을 알게 되면 왼쪽에서 찬다) | 그대로 |
| 재생 중 | 해가 시각을 따라 간다 | 그대로 |
| 해가 짐(`$finish`) | 해가 오른쪽 끝에서 지고, 바 바탕이 월드와 같은 노을빛 | 그대로 |
| 통과 | 트랙이 `--success`로 한 번 찬다 | 지금 칸이 채워지고 ▼가 다음 칸으로 뛴다. 처음 통과한 칸은 해가 진 뒤에 채운다 |
| 실패 | 그대로 | 지금 칸이 좌우로 두 번 흔들린다 |

움직임 줄이기에서는 뜀·흔들림·흐름이 없고 해는 자리만 옮긴다. 상단 바의 다른 안(가볍게: 유형 칩과 진행 막대만, 과감하게: 바 전체를 하늘로)은 시간과 결과가 보이지 않거나 코드를 읽는 데 방해가 되어 고르지 않았다.

폭 1100px 미만에서는 월드, 에디터, 콘솔, 파형 순서로 세로로 쌓는다. 폰에서는 예측형과 숫자 답 스테이지가 편하고, 코드를 고치는 스테이지에는 "PC가 편해요"라고 알려 준다(남은 일).

강의 흐름도 그대로 따른다. 1-2주차 앞부분은 한 모듈에 설계와 테스트벤치를 같이 쓰므로 탭이 하나다. "design/testbench 분리"(스테이지 1-13)부터 탭이 둘이다.

### 6.2 실행 한 번의 흐름

1. 실행을 누른다(Ctrl+Enter). 버튼이 "실행 중"으로 바뀐다. 예측·타이밍형은 답을 먼저 골라야 한다. 보스처럼 `afterRun`인 문제는 실행해서 파형을 본 뒤에 고르고 다시 실행한다.
2. 엔진이 컴파일한다(해의 길이 좌우로 흐른다). 오류면 콘솔에 줄 번호와 함께 띄우고, 에디터의 그 줄에 표시하고 멈춘다.
3. 성공이면 콘솔에 로그가 찍히고 타임라인이 만들어진다.
4. 해가 뜨고(t=0) 월드가 재생된다. 구간마다 바뀐 신호만 원인 순서대로 한 번씩 걷는다: 입력 → 건물(지연 칸이 한 틱씩 찬다) → 그 출력 → 다음 건물. 걷는 동안 시각은 멈추고, 건물에서 한 틱씩 오르고, 다음 자극까지 기다릴 때 넘어간다. 바뀐 길·알파카·건물에 네온이 이어 붙고, 건물을 나온 알파카에 `#3` 꼬리표가 따라가고, 자막이 한 줄로 말한다. 파형의 시각선과 해의 길이 같은 시각을 따른다(7.9).
5. `$finish` 시각에 해가 지고(월드 하늘색과 바 바탕이 노을빛이 된다) 알파카가 모두 문 앞에 서고 결과 판이 뜬다.
6. 맞으면 "다음 스테이지"를 보여 준다. 틀리면 어디서 달라졌는지 한 줄로 말하고("t=15에서 E가 1이어야 하는데 0이에요") "그 시각으로 가기"를 준다.

### 6.3 꼭 있어야 하는 동작

| 동작 | 설명 | 상태 |
| --- | --- | --- |
| 코드와 월드의 양방향 강조 | 코드의 신호 이름에 마우스를 올리면 월드의 그 길이 빛난다. 길을 누르면 코드의 그 신호가 강조된다 | 파형 줄에 마우스를 올리면 길이 빛나는 것까지 |
| 시간 슬라이더 | 끌면 월드, 파형, 콘솔의 강조 줄이 같은 시각으로 움직인다. 그 시각까지의 변화가 모두 끝난 자리로 가서 멈춘다(`msAtTime`). 구간 경계에 눈금 | ✅ |
| 빈칸 | 점선 테두리와 옅은 파랑 배경의 입력 칸. Tab으로 다음 빈칸으로 간다 | ✅ |
| 잠금 줄 | 회색 배경과 자물쇠 표시. 편집할 수 없고, 설계형 스테이지에서는 풀린다 | ✅ |
| 도움 칸 | 문제 설명 바로 아래에 늘 있다. 힌트 1(개념) → 2(위치) → 3(답의 형태) → 정답. 아래 표 | ✅ PR #19 |
| 끝나지 않는 코드 | `$finish`가 없으면 시간·출력 상한에서 멈추고 "해가 지지 않아요. `$finish`가 있는지 봐요"라고 알린다. 상한까지 재생하지 않고 바로 결과 판을 띄운다 | ✅ (감시 모듈, 9.5. 스테이지 1-9) |
| 초기화 | "처음 코드로" 버튼으로 스테이지 시작 코드를 되돌린다. 작성 중인 코드는 스테이지별로 자동 저장한다 | ✅ |

**도움 칸** (`src/app/play/Help.tsx`). 단계 줄은 알약 4개(`힌트 1 · 힌트 2 · 힌트 3 · 정답`)이고 그 아래에 내용이 나온다. 처음에는 "막히면 힌트를 열어요. 봐도 감점이 없어요." 한 줄과 [힌트 보기] 단추만 보인다. 앞 단계를 열어야 다음 단계가 열리고, 정답은 힌트 3을 연 뒤 [정답 보기]를 눌러야 보인다. 연 단계는 알약을 눌러 다시 본다. `<section aria-label="도움">`, 단계는 단추, 열린 내용은 `aria-live="polite"`이고 Tab 순서는 문제 설명 → 도움 칸 → 에디터다. [정답 보기] 단추가 사라질 때는 첫 넣기 단추로 초점을 옮긴다.

| 유형 | 정답 보기에서 보여 주는 것 | 단추 |
| --- | --- | --- |
| 빈칸 | 빈칸이 있는 줄을 정답으로 채우고 채운 곳을 강조 | 빈칸에 넣기 |
| 버그 수정, 변환, 설계 | `solution`의 파일 전체. 시작 코드와 다른 줄을 강조(줄 단위 비교) | 에디터에 넣기 |
| 예측, 타이밍(과 1-4, 보스의 문제 칸) | 답 | 답 고르기 |

정답은 스테이지 JSON의 `solution`에서 만든다(`solutionView`, `src/sim/stage.ts`). 해설은 선택 칸 `explain`이다. 구역 1은 15개 모두 초안이 있다(PR #22. 문구는 주찬이 강의자료로 맞춰 본다, 14.4). 넣기 단추는 값을 채우기만 하고 실행은 사용자가 누른다. 정답을 열면 진행도의 `peeked`에 적는다. 감점이나 잠금은 없고, 스테이지 목록에 `✓ 통과 · 정답 봄`, 징검다리 칸 가운데에 점, 첫 화면의 "틀린 문제 다시 풀기"에 그 스테이지가 먼저 나온다.

문제 유형에 따라 에디터가 달라진다. 예측형은 코드가 읽기 전용이고 보기를 고른 뒤에 재생한다. 타이밍형은 숫자 칸 하나만 있다. 버그 수정·변환·설계형은 파일 전체를 고치는 가벼운 에디터(`CodeEditor.tsx`)를 쓴다. 문법 강조가 필요해지면 그 자리에 CodeMirror를 넣는다. 유형 표는 8장에 있다.

### 6.4 자유 Verilog (연습장)

상단 메뉴의 "자유 Verilog"(`#/free`)는 채점, 결과 판, 힌트 없이 코드를 돌려 보는 화면이다. 구현은 `src/app/free/Free.tsx`다(PR #20, 1차).

- 왼쪽에 에디터 두 탭(`design.sv`, `testbench.sv`), 오른쪽 위에 파형, 오른쪽 아래에 콘솔. 폭 1100px 미만에서는 에디터, 콘솔, 파형 순서로 쌓는다.
- 같은 `WasmRunner`와 제한값을 쓴다. Ctrl+Enter로 실행한다.
- 최상위 모듈은 `findTop`(`src/sim/modules.ts`)이 고른다: 다른 모듈이 인스턴스로 쓰지 않은 모듈, 여럿이면 `initial`이 있는 것, 그래도 여럿이면 마지막 것. 덤프 모듈이 이 이름으로 `$dumpvars(0, top)`을 건다.
- 파형은 최상위 모듈의 신호를 선언 순서대로 모두 그린다. 재생은 없고 시각선을 끌어서 보며, 콘솔은 그 시각의 줄을 강조한다. `$dumpfile` 이름이 `dump.vcd`가 아니면 "파형 파일 이름은 dump.vcd로 써요"라고 알린다.
- 쓰던 코드는 `drafts['free']`에 자동 저장한다. [예제 불러오기]는 `content/verilog/examples.json`의 예제 3개(assign으로 OR·AND, 게이트 지연, always 클럭)를 불러온다. CI의 스테이지 검증이 예제도 컴파일해 본다.
- 2차(나중): 게이트 프리미티브와 연산자 하나짜리 `assign`만 쓴 코드는 장면도 만든다. 코드에서 건물을 읽고 단계마다 열을 나누고, 배치 원칙(9.4)에 맞게 문 자리와 길을 고른다. 그릴 수 없는 코드(`always`, `case`, 벡터, 인스턴스)는 파형과 콘솔만 보여 준다. 모든 코드를 그리는 일(Yosys)은 5단계에 그대로 둔다(13장).

### 7.8 움직임과 소리

- 화면 전환과 버튼은 180ms ease-out이다.
- 월드는 대본 시계로 재생한다. 재생 시간은 틱 수가 아니라 변화의 수가 정한다(1-4는 1×로 7.3초, 1-1은 7.8초). 속도는 0.5×, 1×, 2×다(7.9).
- 정답이면 건물이 한 번 튀고(120ms), 오답이면 동물이 제자리에서 고개를 젓는다. (남은 일)
- `prefers-reduced-motion`이면 알파카는 걷지 않는다. 물결마다 새 값의 알파카가 문 앞에 바로 서고, 걷기 조각은 절반 길이다. 네온 선은 그어지는 움직임 없이 바로 켜진다. 바의 뜀·흔들림·흐름도 없다.
- 소리는 기본이 꺼짐이다. 켜면 발소리, 건물 통과음, 정답 종, 오답, x 안개, 해 지는 소리 여섯 가지가 난다. 음원 파일 없이 코드에서 만든다. (✅ PR #11: Web Audio로 실행, 값 변화 1/0, 안개, 정답 종, 오답, 컴파일 오류. ZzFX 대신 직접 만들었다. 배경음은 `content/audio.json`. 순차 재생에서는 물결이 걷기 시작할 때 한 번 낸다)

### 7.9 움직임 규칙: 순차 재생

한 줄 원칙: **바뀐 값만, 차례대로, 한 번씩 걷는다. 걷는 동안 시간은 멈추고, 시간은 건물에서 숫자로 읽는다.** 구현은 `src/sim/script.ts`(대본), `src/world/beat.ts`(대본 시계), `walkers.ts`·`Walkers.tsx`(걷기, 네온 테두리, 꼬리표), `Trail.tsx`(네온 선), `caption.ts`(자막), `src/sim/delays.ts`(지연 읽기)다(PR #17, #18). v1.4의 박자 시계(모든 길이 10틱마다 걷기, 1틱 240ms)를 대신한다.

1. **변화 한 번에 한 번 걷는다.** 신호 값이 바뀌면 그 길의 알파카가 새 값을 싣고 출발 문에서 나와 문 앞(마지막 칸 가운데)까지 한 번 걷는다. 값이 그대로인 길의 알파카는 문 앞에서 건물을 보고 서서 기다린다. 되풀이해 걷지 않는다.
2. **차례대로 걷는다.** 한 구간 안의 변화를 원인 순서로 재생한다: 입력 → 건물 → 그 출력 → 다음 건물. 같은 때 바뀐 같은 단계의 신호는 같이 걷는다.
3. **구간은 길이와 상관없이 끝까지 재생한다.** 자극 간격이 `#1`이어도 걷기와 건물 통과를 모두 보여 준다. 재생 시간은 틱 수가 아니라 변화의 수가 정한다. `#5` 간격의 구간과 `#10` 간격의 구간은 변화의 수가 같으면 같은 길이다.
4. **걷는 동안 시간은 멈춘다.** 길(wire)에는 지연이 없다. 시각 t는 건물이 지연을 셀 때와 다음 자극을 기다릴 때만 흐른다. 시간 슬라이더, 파형의 시각선, 해의 길도 그때만 움직인다. 그래서 화면의 값은 늘 그 시각의 값이다.
5. **시간은 숫자로 읽는다.** 코드에 쓴 `#N`은 그 건물을 나온 알파카 머리 위의 꼬리표로 따라간다. 건물의 지연 칸은 건물 조각에서 한 틱에 하나씩 찬다.
6. **이번 구간에 바뀐 것은 네온으로 잇는다.** 바뀐 길, 그 길의 알파카, 지나간 건물에 네온 테두리가 원인 순서대로 이어 붙고, 구간이 끝나면 180ms로 꺼진다. 멈춰서 슬라이더로 볼 때는 네온이 없다.
7. **건물은 문으로만 드나든다.** 길 끝은 문 칸이고, 알파카는 문 앞에서 건물을 보고 선다(9.4의 문 규칙).
8. **시계는 하나, 쌓지 않는다.** 모든 움직임은 "대본 위의 위치(ms)" 하나의 함수다. 재생 시계는 기준점 `{ ms, at, speed }`에서 `대본 위치 = 기준 ms + (지금 − 기준 시각) × 속도`를 `requestAnimationFrame`마다 계산하고, 화면의 시각이나 조각이 바뀔 때만 화면 상태를 바꾼다. 알파카, 네온 선, 꼬리표는 같은 프레임 시각으로 한 번 계산한 장면(`scriptView`)을 나눠 쓴다. 컴포넌트마다 타이머를 두지 않는다.

**대본** (`buildScript`). 낱말은 넷이다.

| 낱말 | 뜻 |
| --- | --- |
| 변화 | 장면에 묶인 신호 하나의 값이 어떤 시각에 바뀐 것. 처음 값이 `x`면 변화가 아니다(실행 전에도 안개였다) |
| 단계 | 테스트벤치가 직접 바꾸는 신호는 0. 건물의 출력은 입력 단계의 최댓값 + 1. 입력이 없는 건물(물레방아)의 출력과, `trigger` 없이 자기 입력으로 돌아오는 고리 위의 신호는 0 |
| 물결 | 같은 시각, 같은 단계의 변화 묶음. 같이 걷는다. 이 물결을 내보낸 건물과 코드의 지연을 함께 적는다 |
| 구간 | 단계 0 신호가 바뀐 시각부터 다음에 바뀌는 시각까지. 첫 구간은 t=0에서 시작하고, 마지막 구간은 `$finish`에서 끝난다. 입력은 바뀌었지만 출력은 그대로인 건물을 `quiet`에 적는다 |

`trigger`가 적힌 건물(기억 소자)은 그 입력(클럭, 비동기 리셋)으로만 단계를 센다. D처럼 클럭에 맞춰 읽히는 입력은 원인으로 보지 않는다. 그래서 Q → NOT → D로 돌아오는 회로도 클럭 → 건물 → Q → NOT → D 순서로 선다. 대본은 시간(ms)을 모른다.

**재생 길이** (`beat.ts`). 실제 화면을 보고 바꾸는 값은 이 표뿐이다.

| 이름 | 값 | 뜻 |
| --- | --- | --- |
| `WALK_MS` | 700 | 물결 하나가 걷는 시간. 길 길이와 상관없다(거리는 속도가 흡수한다) |
| `GATE_MS` | 250 | 건물이 문 앞의 값을 읽는 시간 |
| `GATE_TICK_MS` | 150 | 지연 1틱마다 더하는 시간이자 지연 칸 하나가 차는 시간. 6틱까지만 더한다 |
| `GAP_MS` | 300 | 구간 사이. 시각이 다음 자극 시각까지 넘어간다 |
| `STEP_MAX_MS` | 6000 | 한 구간의 상한. 넘으면 그 구간만 같은 비율로 줄인다 |
| `STEPS_PER_WALK` | 4 | 한 번 걷는 걸음 수 |
| `FADE` | 8% | 걷기의 앞 8% 동안 나타난다. 도착해서는 사라지지 않는다 |

| 조각 | 길이 | 시각 t |
| --- | --- | --- |
| 건물 | `GATE_MS + GATE_TICK_MS × min(N, 6)` | `max(앞 물결의 시각, t − N)`에서 `t`까지 한 틱씩 오른다. 지연 칸이 하나씩 찬다. 지연이 없으면 그대로다 |
| 걷기 | `WALK_MS` | 멈춰 있다 |
| 기다림 | `GAP_MS` | 다음 자극 시각까지 고르게 넘어간다 |

`layoutScript`가 조각마다 시작 위치를 미리 계산하고, `frameAt(layout, ms)`가 그 순간의 구간·물결·조각·진행률·시각을, `msAtTime(layout, t)`가 시각 t까지의 변화가 모두 끝난 자리를 돌려준다. 시각은 뒤로 가지 않는다. 지연이 없는 `assign`은 입력과 출력이 같은 시각에 바뀌므로, 화면은 "그 시각의 값이되 아직 걷지 않은 물결의 신호는 옛 값"을 보여 준다(`pendingChanges`). 1-1에서도 A → D → E 차례가 보인다.

| 스테이지 | 재생 | 1× |
| --- | --- | --- |
| 1-4 (`or #3`, `and #2`, 20틱) | 구간마다 입력 걷기 → OR `#3` → w1 걷기(꼬리표 `#3`) → AND `#2` → E 걷기(꼬리표 `#2`) → 기다림. 구간 2의 시각은 10 → 13 → 15 → 20 | 7.3초 |
| 1-1 (`assign`, 40틱) | 걷기가 구간마다 5, 2, 2, 2번. 구간 2의 AND와 구간 4의 OR는 출력이 그대로 | 7.8초 |

**재생 바.** ◀는 이전 구간(구간 가운데에서는 그 구간의 처음), ▶|는 다음 구간이다. 슬라이더는 시간 그대로 두고 구간 경계에 눈금을 단다. `t=13 · 구간 2/4`를 적는다. 건너뛰기(슬라이더, 파형 클릭, 결과 판의 "그 시각으로 가기")는 멈추고 `msAtTime`으로 간다. 멈추면 모든 알파카가 문 앞에 선다. 효과음은 물결이 걷기 시작할 때 한 번 낸다. 해의 길(`--dur-tick`)은 150ms로 따라간다. 끝나지 않는 코드와 탭이 가려질 때 멈추기는 그대로다. 개발용 주소 `?ms=`는 실행한 뒤 그 대본 위치를 그리고 멈춘다(e2e가 1-4의 w1이 걷는 5,400ms를 찍는다).

**지연 칸.** `delaysBySignal`이 실행한 코드(주석 제외)에서 `or #3 (w1, A, B);`, `assign #3 w1 = ...;` 꼴을 찾아 출력 신호별 지연을 읽는다(프리미티브는 첫 포트가 출력, 정수 하나짜리만). 건물의 출력 신호가 시각 c에 바뀌면 그 건물은 c − N부터 c 직전까지 "지나는 중"이다(`passingAt`). 그 건물의 건물 조각에서만 건물 가운데 위에 칸 N개를 그리고 한 틱에 하나씩 채운다(앞 물결이 걷는 동안 다음 건물이 미리 세지 않는다). N이 6을 넘으면 남은 틱 수를 적는다. 출력이 여럿이면 가장 늦게 끝나는 출력의 칸을 그린다. 월드 설명글에도 `OR #3, 3틱 중 2틱째`라고 단다. 표시용이고 채점은 결과로만 한다.

**네온.** 알파카는 같은 그림을 한 벌 더 밑에 깔고 모든 면을 네온 4px 선으로 칠해 필터 없이 테두리를 만든다(번짐 필터는 쓰지 않는다). 길은 가운데를 따라 3px 선이 알파카 뒤로 그어진다(`pathLength`와 `stroke-dashoffset`). 지나는 중이거나 지난 건물은 바닥 테두리가 켜진다. 색만으로 말하지 않는다: 바뀐 신호는 걷고(움직임), 꼬리표가 붙고(글자), 자막이 말한다.

**꼬리표.** 건물을 나온 알파카 머리 위 14px쯤에 그 신호를 내보낸 코드의 지연(`#3`)을 단다. 빈칸에 `#5`를 쓰면 `#5`다. 입력 알파카와 지연이 없는 출력에는 없다. 흰 바탕(`--surface`), 네온 테두리 2px, 글자는 `--text`, 코드 글꼴 12px, 굵기 800이다. 걷는 동안과 구간이 끝날 때까지 보인다.

**자막** (`caption.ts`). 월드와 재생 바 사이 한 줄이고 `aria-live="polite"`다. 신호 이름 뒤에는 조사를 붙이지 않는다(영문 이름이라 받침을 알 수 없다). 좁은 화면에서는 두 줄 자리를 늘 비워 둔다.

| 순간 | 자막 |
| --- | --- |
| 구간 시작(입력이 걷는다) | `구간 2/4 · t=10 · 입력이 바뀌었어요 (A: 0 → 1)` |
| 건물, 지연 있음(그 출력이 걷는 동안에도) | `OR #3 · 3틱 뒤 t=13에 w1: 0 → 1` |
| 건물, 지연 없음 | `OR · 바로 D: 0 → 1` |
| 기다림, 출력이 그대로인 건물이 있을 때 | `AND · 입력이 바뀌어도 출력(E)은 그대로예요` |
| 기다림 | `다음 입력까지 5틱 · t=20` |
| 해가 짐 | `t=40 · 해가 졌어요` |

**층.** 땅 → 네온 선 → 건물과 알파카(칸 순서대로 섞는다) → 이름표(길, 건물, 문) → 꼬리표. 알파카는 서 있는 칸의 그리는 순서((i + j, i))대로 건물 묶음 사이에 끼워 그려서, 건물 뒤 칸(위 문, 뒤 문)에 선 알파카는 건물에 가려진다. 자리가 바뀔 때만 DOM을 옮긴다. 섬 지도는 예외로 한 칸에 0.8초(칸 걷기)로 늘 걷는다.

고르지 않은 안: 박자마다 모든 길이 걷기(v1.4. 바뀐 것이 묻힌다), 구간마다 모든 길이 한 번씩 걷기(그대로인 값도 움직인다), 박자마다 걷되 바뀐 길만 네온(되풀이하는 움직임이 그대로다), 틱 길이는 고르게 두고 짧은 구간만 늘이기(규칙이 둘이 된다), 알파카가 건물 안으로 들어가 사라지기(지금 입력 값이 화면에서 없어진다), 꼬리표에 누적 시간(`#3 + #2 = 5`, 글자가 길어진다), 보라 네온(x의 안개색과 가깝다).

### 8.2 무엇을 비우는가

1. 한 스테이지는 개념 하나다. 그 슬라이드가 가르치는 한 가지만 비운다.
2. 강의자료에서 강조한 줄이 빈칸 후보다. 예: `or #3(w1,A,B);`, `test ins_name(H,A,B,C);`, `$dumpvars(1);`, `output reg [1:0]Y;`, `casez(D)`.
3. 교수님이 비워 둔 칸은 그대로 스테이지로 삼는다. 1-2주차 18쪽(회로도를 보고 게이트 작성), 6-7주차 5쪽(prefix tree의 `G_ij` 연결).
4. 점점 넓힌다. 토큰 하나, 한 줄, 블록, 파일 전체 순서다.
5. 빈칸이 아닌 줄은 초반에 잠그고, 설계형에서 푼다.

### 8.3 문제 유형 6가지와 문제 칸 (✅ 화면 모두 있다)

| 유형 | `type` | 사용자가 하는 일 | 예 | 월드 연출 |
| --- | --- | --- | --- | --- |
| 예측 | `predict` | 코드를 보고 출력·파형을 맞힌다 | 지연이 있을 때 t=15의 E, 초기화 안 한 reg의 값 | 답을 고른 뒤 재생해서 확인 |
| 빈칸 | `fill` | 토큰 하나나 한 줄을 채운다 | 게이트 줄, 인스턴스 줄, `$monitor` 형식 | 채우면 길이 이어지고 동물이 지나간다 |
| 버그 수정 | `fix` | 틀린 코드를 고친다 | 프리미티브 포트 순서(출력이 맨 앞), `$finish` 누락, reg/wire 혼동 | 동물이 엉뚱한 곳으로 간다 |
| 변환 | `convert` | 같은 동작을 다른 문법으로 쓴다 | `forever` → `repeat`, `assign` → `bufif1`, `case` → `if` | 두 마을의 결과가 같아야 통과 |
| 설계 | `design` | 모듈을 처음부터 쓴다 | 8:1 MUX(계층), 8-bit RCA, 16-bit prefix adder | 빈 터에 건물이 지어진다 |
| 타이밍 | `timing` | t\_cd, t\_pd 같은 숫자를 답한다 | XOR 회로 지연, RCA 지연 | 경주 기록판 |

문제 칸(`question`)은 네 가지다. 정답을 적어 두지 않고 시뮬레이션 결과와 비교한다(숫자 답만 예외).

| `question.kind` | 묻는 것 | 쓰는 곳 |
| --- | --- | --- |
| `choice` | 시각 `time`에서 신호 `signal`의 값 | 1-2, 1-4, 1-5, 1-6 |
| `number` | 숫자 하나(`answer`) | 1-11 |
| `dumped` | 신호가 파형(VCD)에 적히는가. `choices[0]`이 "적힌다", `choices[1]`이 "안 적힌다" | 1-14 |
| `expr` | 파형에 맞는 불 함수(Verilog 식). 입력이 바뀌기 직전의 자리 잡은 값으로 비교한다(`src/sim/expr.ts`) | 1-15 |

기본은 답을 먼저 고르고 실행한다. `afterRun: true`면 답 없이 실행해 파형을 보고, 고른 뒤 다시 실행한다. 빈칸과 문제 칸을 함께 쓰는 스테이지(1-4, 1-15)는 결과 판이 코드의 실패를 먼저, 답의 실패를 나중에 말한다. 문제 칸 아래의 "맞아요"는 답만 본다.

## 9. 기술 설계

서버는 없다. 사용자의 코드는 브라우저 안의 Icarus Verilog가 돌리고, 결과를 "타임라인"이라는 한 형식으로 바꿔 월드·파형·채점기가 함께 쓴다.

**그림을 글로 옮김 (구조):** 스테이지 데이터(JSON: 시작 코드, 장면, 채점 규칙) →(시작 코드)→ 에디터(design.sv, testbench.sv) →(실행)→ Runner(Web Worker 안에서 ivlpp → ivl → vvp) →(로그, VCD)→ 타임라인(시각마다 신호 값) → 월드, 파형, 채점기. Runner는 갈아 끼울 수 있다(네이티브, 미리 계산한 결과).

장면과 채점 규칙도 스테이지 데이터에서 온다. 화면 코드는 `Runner`와 `Timeline` 두 형식만 알고, 엔진이 무엇인지는 모른다.

### 9.2 Runner: 엔진을 갈아 끼우는 경계

`src/runner/types.ts`에 있다.

```ts
export interface RunRequest {
  files: { name: string; text: string }[]; // design.sv, testbench.sv
  top: string;                             // 최상위 모듈 이름
  limits?: { simTime?: number; logLines?: number; wallMs?: number };
}
export interface RunResult {
  ok: boolean;                 // 컴파일 성공 여부
  stage: 'compile' | 'run';
  log: string;                 // $monitor, $display 출력
  diagnostics: { file: string; line: number; message: string }[];
  vcd?: string;                // dump.vcd 원문
  timedOut: boolean;
}
export interface Runner { run(req: RunRequest): Promise<RunResult>; }
```

구현은 셋이다. `WasmRunner`(`wasmRunner.ts` + `worker.ts`)가 기본이고, `FixtureRunner`는 미리 계산한 결과를 돌려주는 테스트용이며(⬜, `engine/golden/*/native/`가 그 데이터다), `NativeRunner`는 대안 B를 쓸 때만 만든다.

세 단계 호출은 `src/runner/iverilog.ts`의 `runIverilog()`에 있고, 브라우저 워커와 Node 골든 테스트가 같은 코드를 쓴다. ivl 설정 파일은 iverilog 드라이버를 흉내 내고 `-g2012`(SystemVerilog-2012)로 컴파일한다.

스테이지 1-14에서 `$dumpvars`를 배우기 전에는 코드에 파형 덤프 줄이 없다. 그동안은 Runner가 덤프용 모듈(`__kwss_dump`)을 함께 컴파일해서 VCD를 얻는다. Icarus Verilog는 인스턴스가 없는 모듈을 최상위로 다루므로 따로 연결할 필요가 없다.

건물의 선택 칸(PR #16, #17):

- `in`과 `out`은 이름 하나, 목록, 객체 가운데 하나로 적는다. 목록은 이름 없는 문이고(신호 이름만 적는다), 객체는 `문 이름: 신호 이름`이다. 순차 재생의 단계 계산(7.9)과 코드의 지연 세기에 쓴다. 없는 건물(1-7의 기록원, 1-12)은 지금처럼 그리기만 한다. 1-9·1-10의 물레방아는 `out`만 있다.
- `size`는 [가로(흐름 방향), 세로]이고 기본은 [1, 1]이다. `at`은 왼쪽 위 칸이다.
- `trigger`는 기억 소자의 클럭 입력이다(7.9). 메모리 구역을 만들 때 쓴다.
- v1.4의 `beatTicks`는 지웠다.

```json
{ "id": "fa0", "label": "FA", "at": [3, 1], "size": [1, 3],
  "in": { "cin": "c0", "b": "b0", "a": "a0" }, "out": { "s": "s0", "cout": "c1" } }
```

**문 규칙** (`src/world/doors.ts`, `tests/doors.test.ts`). 신호는 +x 방향(화면에서 오른쪽 아래)으로 흐른다. "위"는 위에서 내려다본 지도의 위쪽(j가 작은 쪽)이다. 왼쪽 화면은 푸는 사람이 고치는 화면이 아니라 스테이지를 만들 때 한 번 정하는 그림이라, 문 자리를 규칙으로 묶지 않고 길이 건물에 닿는 곳을 문으로 삼는다. `gateDoors(scene, gate)`가 길의 칸에서 문을 찾아 `[{ port, signal, dir, cell, face, inner }]`를 돌려주고, 장면 검사·그리기·걷는 길이 모두 이 함수를 쓴다.

| 면 | 문 칸 (건물 (i, j), 크기 w×h) | 화면에서 | 주로 |
| --- | --- | --- | --- |
| 위 | (i+k, j−1) | 오른쪽 위. 가려지는 면 | 입력 |
| 뒤 | (i−1, j+k) | 왼쪽 위. 가려지는 면 | 입력 |
| 아래 | (i+k, j+h) | 왼쪽 아래. 보이는 면 | 입력 |
| 앞 | (i+w, j+k) | 오른쪽 아래. 보이는 면 | 출력 |

꼭 지키는 것(검사가 실패로 잡는다):

1. 문은 길이 건물에 변으로 닿는 자리에 생긴다. 입력 길은 마지막 칸이, 출력 길은 첫 칸이 건물 옆 칸이다. 대각선 칸은 문이 아니다.
2. 건물이 `in`과 `out`에 적은 신호에는 모두 문이 있다.
3. 길의 칸은 이어져 있다. 길, 건물, 집은 서로 겹치지 않는다(문 칸 하나에는 길 하나).
4. 이름 없는 입력 문은 위아래 대칭이다: 1개는 뒤, 2개는 위아래, 3개는 위아래와 뒤, 4개는 위 2·아래 2. AND, OR, XOR처럼 입력끼리 바꿔도 되는 게이트가 여기에 든다.
5. 이름 있는 문(모듈, 플립플롭, 메모리)은 자리가 자유다. 문마다 이름표가 붙는다.
6. 값을 받는 집은 길 끝이 집의 아래쪽 옆 칸 (i, j+1)이나 뒤 칸 (i−1, j)에 닿는다. 값을 내보내는 집(reg)은 앞 칸 (i+1, j)에서 길이 시작한다.

배치 원칙(검사가 경고로 알린다): 출력 문은 앞면이 기본이다. 이름 있는 문은 데이터를 뒤에, 제어(선택, 클럭, enable, we)를 위나 아래에 둔다. 건물 크기는 문 사이를 한 칸씩 띄울 수 있는 가장 작은 크기로 하고(입력 3개·출력 1개까지는 1×1), 띄울 자리가 없으면 문을 붙인다. 서로 다른 신호의 길은 붙은 문 칸 말고는 변이 맞닿지 않게 한 칸 띄운다. 길은 2~6칸(가장 긴 길이 가장 짧은 길의 2.5배 이하), 꺾임은 두 번까지다. 같은 모양의 회로는 같은 배치를 쓰고(두 건물 계단: 1-1, 1-4, 1-8, 1-11), 벡터는 길 하나, 문 하나로 센다.

그리기: 넓은 건물은 칸마다 한 조각씩 그린다(큰 상자 하나를 한 칸에 넣으면 그 뒤 칸의 땅이 건물을 덮는다). 건물 이름표와 지연 칸은 건물 가운데 위에 둔다. 보이는 면(아래, 앞)의 문 자리에는 문을 그린다. 이름 있는 문은 문 칸과 건물이 만나는 변 바로 바깥에 11px 이름표를 단다(가려지는 면은 지붕 높이에 띄운다). 서로 다른 길이 맞닿으면 경계선(2px)을 긋는다. 걷는 알파카는 출발 건물 쪽 변에서 나오고, 마지막 반 칸에서 도착 건물 쪽으로 꺾어 문 앞에 선다(`WalkPath.from`·`to`). 넓은 건물의 견본(입력 4개 AND 2×1, 전가산기 릴레이 1×3 두 채, 메모리 1×3)은 `src/world/samples.ts`에 있고 `#/ui`와 문 검사가 쓴다. `solution`의 키는 빈칸 id, 파일 전체는 `file:이름`, 예측·타이밍 답은 `answer`다. 자유로운 코드에서 장면을 자동으로 만드는 일은 자유 Verilog 2차(6.4)와 5단계로 미룬다.

### 9.5 제한값과 엔진 파일

- 시뮬레이션 시간 10,000틱, 로그 2,000줄, 실행 5초가 시작값이다(`DEFAULT_LIMITS`). 시간 상한은 감시 모듈(`__kwss_guard`: `initial #10000 $finish;`)을 함께 컴파일해서 건다. 그래도 워커가 답하지 않으면 워커를 끝내고 새로 만든다.
- 엔진 파일(js·wasm 세 쌍)은 사이트의 `engine/` 폴더에 있고, 첫 실행 때 받아 브라우저 캐시에 둔다. 플레이 화면에 들어오면 미리 받기 시작한다(`warmUp`). 진행 표시는 상단 바의 해의 길이 맡는다(실행 중에 좌우로 흐른다. 받은 비율을 Runner가 알려 주면 왼쪽에서 차게 바꾼다).
- 엔진 파일은 저장소에 넣지 않는다. 빌드 때 `node engine/fetch-engine.mjs public/engine`이 이 저장소의 `engine-v0.1.0` Release에서 받아 sha256을 확인한다(`engine/engine.lock.json`). 새 엔진은 `engine.yml`을 `release_tag`와 함께 수동 실행해 내고 lock 파일을 바꾼다.
- 워커는 스레드와 `SharedArrayBuffer` 없이 돈다. GitHub Pages에서는 그에 필요한 응답 헤더를 설정할 수 없다.
- 사용자에게 보이는 로그와 오류에서는 감시·덤프 모듈의 흔적을 지우고, 파일 경로를 이름만 남긴다(`testbench.sv:14:`).

## 11. GitHub 업로드와 배포 계획

main에 합치면 GitHub Actions가 빌드해서 GitHub Pages에 올린다. 사람이 손으로 파일을 올리는 단계는 없다.

### 11.1 처음 한 번 할 일

| # | 할 일 | 상태 |
| --- | --- | --- |
| 1 | GitHub에 저장소 만들기 | ✅ `Setter1324/StudyVerilog` |

### 11.2 브랜치와 커밋

- `main`은 항상 배포할 수 있는 상태로 둔다.
- 작업은 `feat/...`, `engine/...`, `docs/...` 브랜치에서 하고 PR로 합친다. CI가 통과해야 합친다.
- 커밋 머리말은 `feat:`, `fix:`, `content:`(스테이지), `engine:`, `docs:`, `chore:`를 쓴다.
- 강의자료 PDF와 캡처는 커밋하지 않는다. `.gitignore`에 `lecture/`가 있다.

### 11.3 워크플로 네 개

| 파일 | 언제 도나 | 하는 일 | 상태 |
| --- | --- | --- | --- |
| `ci.yml` | 모든 PR과 main push | `check`: 설치, 엔진 받기, 타입 검사, 린트, 단위 테스트, 빌드. `golden`: 네이티브 대 wasm 골든 비교, 스테이지 검증 | ✅ |
| `deploy.yml` | main에 push, 수동 실행 | 설치, 엔진 받기, 빌드, Pages 배포 | ✅ |
| `engine.yml` | 수동 실행(`release_tag` 입력), `engine-v*` 태그, `engine/build/**`를 바꾼 PR | iverilog를 WebAssembly로 빌드하고 골든 비교. `release_tag`나 태그가 있으면 Release 자산으로 올린다 | ✅ `engine-v0.1.0` 출시 |
| `shots.yml` | 모든 PR, 수동 실행 | 빌드를 미리보기로 띄워 스크린샷, 임시 Playwright로 스테이지 몇 개를 실제로 풀기. 스크린샷은 로그에 base64로도 남긴다 | ✅ |

배포 워크플로는 Vite 공식 문서의 GitHub Pages 예시를 따른다. Vite의 `base`는 `/StudyVerilog/`가 기본이고 환경 변수 `VITE_BASE`로 바꿀 수 있다. Actions 실행 로그에 "Node.js 20 is deprecated"(`actions/checkout@v4`, `setup-node@v4`) 경고가 뜬다. 지금은 동작하니, 새 메이저 버전이 나오면 올린다.

### 11.4 주소와 COM's 연결

- 배포 주소는 `https://setter1324.github.io/StudyVerilog/`다.
- COM's 사이트에는 Apps 목록에 등록을 요청한다. 목록은 운영 패널에서 관리한다. 분류는 "웹", 한 줄 소개는 "Verilog 수업을 블록 마을에서 복습하는 학습 게임"으로 한다.

## 13. 로드맵과 완료 기준

첫 출시는 2단계가 끝나는 때다. 날짜는 정하지 않았고, 각 단계는 완료 기준을 통과해야 다음으로 넘어간다.

**그림을 글로 옮김 (로드맵):** 0 엔진 검증 →[관문: 골든 테스트 6개 일치]→ 1 세로 한 줄 →[관문: Pages에서 1-1 통과]→ 2 구역 1 완성 →[관문: v0.1.0 출시, COM's Apps 등록]→ 3 깊이 더하기 → 4 구역 2~6. 이후 선택: 5 앱 설치와 자유 모드, 6 C/C++ 팩.

여기의 "단계"(0~6)는 제품 로드맵이고, 14.2절의 "번호"(1~7)는 작업 순서다. 지금은 작업 순서 1~6번이 끝났고 7번(스테이지 채우기)은 15개 초안까지 했다. 로드맵으로는 1단계까지 끝났고 2단계 중이다. 5단계의 "자유 모드"는 셋으로 나눴다: 연습장(자유 Verilog 1차, PR #20), 게이트 코드에서 장면 만들기(2차, PR #16·#17 뒤), 모든 코드의 회로도(Yosys, 5단계에 그대로).

## 15. 위험과 대응, 저작권과 라이선스

가장 큰 위험이던 "브라우저 엔진의 결과가 수업과 다른 경우"는 0단계에서 골든 6개로 확인했다. 구역마다 새 문법의 골든을 더해 계속 확인한다.

| 위험 | 대응 |
| --- | --- |
| 브라우저 엔진의 결과가 수업(EDA Playground)과 다르다 | 골든 테스트로 확인한다. 버전 차이로 생기는 차이는 도감에 적는다. 풀리지 않으면 대안 B로 간다 |
| 수업에서 쓴 문법 중 엔진이 지원하지 않는 것이 있다 | 구역을 만들기 전에 그 문법의 골든 프로그램부터 돌린다 |
| 엔진 파일을 받느라 첫 실행이 느리다 | 첫 실행 때만 받고 캐시한다. 플레이 화면에 들어오면 미리 받는다. 예측형 스테이지는 미리 계산한 결과로 엔진 없이 여는 방법도 있다 |
| 스테이지마다 장면을 손으로 만드는 부담 | 장면은 작업장·길·집 배치(JSON)로 쓴다(`SceneSpec`). 문 검사(`tests/doors.test.ts`)가 배치의 실수를 잡고 배치 원칙을 경고로 알린다(9.4) |
| 범위가 크다(여섯 구역) | 구역 1만으로 출시한다. 그 뒤는 데이터를 더하는 일이다 |
| 폰에서 코드 편집이 불편하다 | 폰에서는 예측형과 숫자 답을 권하고 나머지는 PC를 안내한다 |
| 브라우저 저장이 지워져 진행도를 잃는다 | 설정 판에 진행도 내보내기와 가져오기를 둔다 |
| 끝나지 않는 코드 | 감시 모듈로 시간 상한을 걸고, 그래도 안 끝나면 워커를 끝낸다(9.5) |
| 세션 환경에서 npm·일부 GitHub API가 막힌다 | CI에 맡기고, GitHub 웹 설정은 주찬이 한다(0.3) |
| 초안 스테이지의 문구·정답이 수업과 다르다 | `draft` 표시를 두고 주찬이 강의자료로 확인한 뒤 지운다 |

### 15.1 저작권과 라이선스

법률 자문이 아니라 오픈소스에서 흔히 따르는 방식을 정리한 것이다.

- **앱 코드: MIT로 확정**(2026-11-16, 주찬). 저작권 표시는 `Copyright (c) 2026 김주찬`.
- **엔진:** Icarus Verilog는 GPL-2.0-or-later다. wasm을 사이트로 배포하면 그 소스도 제공해야 한다. 고정한 커밋·패치·빌드 스크립트를 `engine/`에 두고, `engine/` 안에 GPL 전문(`engine/COPYING`)을 둔다. 엔진은 워커에서 별도 프로그램으로 돌고 화면 코드는 그것을 불러 쓰기만 하므로, 화면 코드는 MIT로 둔다. 엔진에 넣는 패치는 GPL을 따른다.
- **강의자료:** PDF와 캡처는 사이트와 저장소에 싣지 않는다. 문제는 같은 개념을 새 코드로 다시 쓴다. 강의 코드를 거의 그대로 써야 하는 스테이지는 교수님께 먼저 여쭤본다.
- **그림과 소리:** 마인크래프트의 텍스처·캐릭터·효과음은 Mojang 소유라 쓰지 않는다. 그림은 직접 그리고, 밖에서 가져오는 에셋은 CC0만 쓴다.
- **글꼴:** Pretendard, JetBrains Mono, D2Coding은 OFL이다. 라이선스 파일을 글꼴과 함께 둔다. 예약 글꼴 이름 조항 때문에 직접 서브셋하지 않는다(7.5).
- **이름과 색:** COM's의 색을 쓰지만 학교나 동아리의 공식 사이트로 보이지 않게 한다. 바닥글에 "COM's 부원 프로젝트"라고 적는다.
